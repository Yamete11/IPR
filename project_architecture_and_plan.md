# Архитектурная схема проекта

* **Симулятор датчиков (Java):** Генерирует и шлет миллионы метрик (температура кабеля, давление в трубах, напряжение на подстанции) в Kafka.
* **Ingestion Service:** Слушает Kafka и распределяет данные: метрики пишет в TimescaleDB, а топологию сети и связи — в Postgres AGE.
* **AI Worker:** Слушает топик критических алертов из Kafka, собирает контекст из баз данных, делает запрос к Claude API и сохраняет готовый план ликвидации аварии.
* **Инфраструктура:** Все это разворачивается локально в кластере Kubernetes.

# Детальный план реализации проекта

## Этап 1: Инфраструктурный базис и Сбор данных (Kafka + Базовый K8s)
**Срок:** Недели 1–4  
**Ключевые задачи:** Настройка среды и организация бесперебойного потока данных.

* **Развертывание окружения:** Установить локальный Kubernetes-кластер (Minikube или Kind). Развернуть внутри кластера Apache Kafka (рекомендуется использовать оператор, например, Strimzi Kafka Operator, так как это стандарт индустрии).
* **Разработка симулятора датчиков:** Написать легковесный сервис, который имитирует работу 1000 датчиков «Умного города». Сервис должен генерировать JSON-сообщения (`timestamp`, `sensor_id`, `metric_type`, `value`, `status`) и с высокой частотой отправлять их в топик Kafka `city-telemetry`.
* **Создание Ingestion-сервиса:** Написать базовый бэкенд-сервис внутри K8s, который считывает данные из топика `city-telemetry` (Kafka Consumer) и просто выводит их в лог, подтверждая стабильность соединения и пропускную способность под нагрузкой.

## Этап 2: Хранение и Аналитика (TimescaleDB + PostgreSQL AGE)
**Срок:** Недели 5–8  
**Ключевые задачи:** Организация гибридного хранения — метрики по времени + граф связей.

* **Развертывание БД в K8s:** Запустить в Kubernetes инстанс PostgreSQL с предустановленными расширениями TimescaleDB и Apache AGE (можно использовать готовый Docker-образ или настроить через Helm).
* **Реализация Time-Series слоя (TimescaleDB):**
  * Создать таблицу для метрик телеметрии и преобразовать её в гипертаблицу (Hypertable) с секционированием по времени.
  * Доработать Ingestion-сервис, чтобы он записывал поток метрик из Kafka в эту гипертаблицу.
  * Написать SQL-запросы для расчета скользящего среднего значения показателей датчиков за последние 5 минут (Continuous Aggregates).
* **Реализация Графового слоя (PostgreSQL AGE):**
  * Спроектировать граф топологии городской инфраструктуры. Вершины (Vertices): Подстанция, Распределительный узел, Жилой дом, Датчик. Ребра (Edges): Линия электропередачи, Трубопровод, Связь датчика с узлом.
  * Написать Cypher-запросы (внутри SQL) для поиска зависимостей. Например: «Найти все жилые дома, которые зависят от Распределительного узла №5».

## Этап 3: Интеллектуальный слой (Интеграция с Claude API)
**Срок:** Недели 9–12  
**Ключевые задачи:** Автоматизация выявления аварий и подключение LLM для генерации решений.

* **Детектор аномалий:** Добавить в систему логику, которая фиксирует критические сбои (например, если Continuous Aggregate в TimescaleDB показывает, что давление в трубе упало до нуля, или температура трансформатора превысила 120°C). При фиксации сбоя сервис отправляет событие в новый топик Kafka — `infrastructure-alerts`.
* **Разработка AI-Воркера (Интеграция с Claude):**
  * Написать сервис `AI-Incident-Responder`, который слушает топик `infrastructure-alerts`.
  * При получении алерта сервис делает два запроса в БД: в TimescaleDB (за историей метрик этого датчика за последний час) и в PostgreSQL AGE (чтобы вытащить граф зависимостей и понять, какие объекты инфраструктуры и дома пострадают из-за падения этого узла).
  * Сервис формирует структурированный промпт и отправляет его в Claude API (Anthropic).
* **Генерация инцидент-репорта:** Claude должен вернуть структурированный ответ (например, в формате JSON), содержащий: Степень критичности, Список потенциально пострадавших объектов, Пошаговую инструкцию по локализации аварии для ремонтной бригады. Этот ответ сохраняется в таблицу инцидентов.

## Этап 4: Production-Ready Инфраструктура в Kubernetes
**Срок:** Недели 13–16  
**Ключевые задачи:** Упаковка, обеспечение отказоустойчивости и финальное демо.

* **Оркестрация и Масштабирование:**
  * Написать Helm-чарты для всех собственных микросервисов (Симулятор, Ingestion, AI-Worker).
  * Настроить Horizontal Pod Autoscaler (HPA) для Ingestion-сервиса. Проверить, что при искусственном увеличении нагрузки от симулятора датчиков, Kubernetes автоматически увеличивает количество подов инжекторов для разбора очереди из Kafka.
* **Конфигурация и Безопасность:** Вынести все чувствительные данные (ключи API Claude, доступы к PostgreSQL) в Kube Secrets. Использовать ConfigMaps для управления адресами брокеров Kafka и БД.
